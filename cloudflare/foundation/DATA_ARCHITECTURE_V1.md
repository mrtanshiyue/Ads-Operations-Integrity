# Ads Operations Integrity — Cloudflare Data Architecture V1

## Decision

The new Cloudflare data layer is built from scratch. It does not import or inherit any TiDB schema or data.

Production uses one Control D1 plus one physical Store D1 per Amazon store:

- `ads-ops-control-prod`
- `ads-ops-store-01-prod`
- `ads-ops-store-02-prod`
- `ads-ops-store-03-prod`
- `ads-ops-store-04-prod`

Initial development uses a smaller isolated pair to avoid consuming unnecessary D1 database slots before the account plan is confirmed:

- `ads-ops-control-dev`
- `ads-ops-store-dev`

When the production model is stable, development can be expanded to four store databases if useful.

## Why the databases are split

The Control D1 stores organization-wide identity, RBAC, store routing, master products, keyword governance, negative-keyword governance, optimization rules, cross-store summaries, and audit events.

Each Store D1 stores only one Amazon store's Ads entities, report ingestion state, daily facts, and optimization action ledger. Store databases never share Amazon OAuth credentials. Credentials belong in Cloudflare Secrets Store, not D1.

This split provides blast-radius isolation, simpler store lifecycle management, clearer permissions, and predictable growth. It is not an Amazon-account anti-linking mechanism; Amazon authorization isolation is handled at the OAuth/token boundary.

## Data types and invariants

1. Amazon identifiers are stored as `TEXT`. Never coerce Amazon IDs into JavaScript numbers.
2. Monetary values are stored as integer micros. Example: USD 12.345678 is `12345678` micros.
3. Calendar dates are ISO `YYYY-MM-DD` strings.
4. Application IDs are UUID strings generated by the Worker.
5. D1 contains queryable normalized data. Original Amazon report payloads are retained in R2.
6. Derived ratios such as ACoS, ROAS, CTR, CVR, and CPC are calculated from base measures, not persisted as authoritative facts.
7. External enum values such as Amazon campaign state and ad product remain `TEXT` so upstream enum additions do not break ingestion.
8. Cross-database references (`store_id`, `product_id`, canonical `keyword_id`) are validated by application code because D1 foreign keys do not cross databases.

## Idempotency contract

Every Amazon report request receives a deterministic `idempotency_key` built from at least:

`store + profile + ad_product + report_type + start_date + end_date + report_config_version`

`report_jobs.idempotency_key` is unique. Re-running a Workflow must reuse the existing job or safely continue it.

Fact tables use stable primary keys and are written with UPSERT semantics. A retry therefore replaces the same logical fact instead of creating a duplicate.

For rows without an Amazon entity ID (search terms, product reports, placements), ETL generates a deterministic SHA-256 `row_key` from the logical dimensions of the row.

## Control D1 domains

- Identity: `users`, `app_roles`, `role_permissions`, `user_global_roles`
- Store access: `stores`, `store_members`
- Product master: `products`, `product_store_map`
- KeywordOS: `keyword_library`, `keyword_product_map`, `keyword_store_policy`
- Negative governance: `negative_keyword_library`, `negative_store_scope`, `negative_product_scope`
- Rules: `optimization_rules`
- Cross-store BI: `store_daily_summary`, `product_daily_summary`, `keyword_performance_rollup`
- Operations: `store_sync_status`, `audit_log`, `app_settings`

## Per-store D1 domains

### Amazon entity mirror

- `amazon_profiles`
- `portfolios`
- `campaigns`
- `ad_groups`
- `keywords`
- `targets`
- `product_ads`
- `negative_keywords`
- `negative_targets`

Entities are soft-retained by upstream `state`; they are not normally deleted when Amazon archives them.

### Report and sync control

- `sync_runs`
- `report_jobs`
- `sync_watermarks`
- `data_quality_issues`

### Queryable daily facts

- `campaign_daily`
- `ad_group_daily`
- `keyword_daily`
- `target_daily`
- `search_term_daily`
- `advertised_product_daily`
- `purchased_product_daily`
- `placement_daily`

Common operational metrics are columns. Less-common or product-specific metrics can be retained in `metrics_json`, while the complete source payload remains in R2.

### Optimization ledger

- `optimization_actions`
- `optimization_action_events`

No bid, budget, state, keyword, or negative-target write should call Amazon directly from the browser. The browser proposes an action; the backend validates RBAC, records a ledger entry, applies the external mutation, and records the result.

## Attribution policy

The schema deliberately does not hard-code a single Amazon attribution window into table names. The ingestion adapter must define a versioned canonical conversion policy per report type and retain source-specific metrics in `metrics_json`/R2. This avoids silently mixing incompatible attribution windows.

## Query policy

- UI store-detail queries hit exactly one Store D1.
- Organization dashboards hit Control D1 rollups.
- The web request path does not fan out to all four Store D1 databases for normal dashboard loads.
- Cross-store rollups are refreshed asynchronously after store ingestion succeeds.
- Date/filter columns used by dashboards must be indexed before the dashboard is released.

## Location

Recommended initial D1 and R2 location hint: `apac`, because the operating users are in the Asia-Pacific region. Location hints are performance hints, not jurisdiction guarantees. No jurisdiction restriction is proposed unless a legal requirement is identified.

Read replication should be evaluated after production query patterns are measured. It is not required for V1 correctness.

## Secrets boundary

Never store these in D1, R2 object metadata, GitHub, browser localStorage, or frontend JavaScript:

- Amazon client secret
- Amazon refresh tokens
- OAuth state/signing secrets
- Cloudflare API tokens
- application signing keys

They belong in Cloudflare Secrets Store / Worker secret bindings.

## Migration discipline

Control and Store schemas have independent migration directories. Migrations are append-only after production provisioning. Never edit an already-applied production migration; create a new numbered migration.

Before applying a migration remotely:

1. Apply it to a clean local SQLite database.
2. Run `PRAGMA foreign_key_check`.
3. Run representative UPSERT and dashboard queries.
4. Apply to dev D1.
5. Validate dev.
6. Apply to production by database name, never by an ambiguous binding alias.
